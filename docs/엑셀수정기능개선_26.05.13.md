# 엑셀수정 기능 개선 인계 - 2026.05.13

## 작업 배경

`엑셀수정` 기능에서 특히 `확정 및 저장`이 느리다는 문의가 있었고, 실제 서버 로그를 기준으로 병목을 확인한 뒤 안전한 범위에서 최적화를 진행했다.

이번 작업은 웹 전용 구조를 기준으로 진행했으며 Electron/IPC 쪽 신규 의존은 추가하지 않았다.

## 수정 파일

- `backend/python/app/main.py`
- `src/view/features/excel-web/pages/ExcelWebEditPage.jsx`

## 확인한 기준 로그

### 개발서버와 운영서버 차이

개발서버는 `npm run start:dev` 환경이라 프론트/파이썬 로그가 한 터미널에 같이 보인다.  
운영서버는 PM2로 분리되어 있어서 파이썬 백엔드 로그는 아래 명령으로 보는 것이 맞다.

```bash
pm2 logs company-search-excel-backend --lines 100
```

### 초기 측정 결과

신용평가 저장의 초기 로그는 대략 아래처럼 나왔다.

```text
[excel-edit:save] status=success fileType=신용평가 saveMode=normal ... validate=1.29s credit_update=3.31s company_lookup=1.20s total=5.80s
```

단일 경영상태 저장은 상대적으로 빨랐다.

```text
[excel-edit:save] status=success fileType=소방경영상태 saveMode=normal ... validate=0.47s company_find=0.31s management_update=0.49s total=1.27s
```

결론:

- 경영상태 1개 수정은 구조상 충분히 빠른 편
- 신용평가는 전기/통신/소방 3개 DB를 모두 건드리므로 더 느린 것이 자연스러움
- 다만 중복 열기, 중복 재조회는 줄일 수 있음

## 구현 완료 내용

### 1. `company_lookup` 중복 워크북 오픈 제거

기존에는 `find`, `extract`, `cells`를 각각 별도 워크북 열기로 처리할 가능성이 있었다.

이 작업에서 아래 형태로 정리했다.

- 워크북을 한 번 연다
- 같은 workbook 안에서
  - 업체 위치 찾기
  - 데이터 추출
  - 셀 색상/서식 추출
  를 모두 처리한다

적용 대상:

- 전기/통신/소방/신용평가 공통 조회

### 2. 저장 시 `validate` 중복 워크북 오픈 제거

저장 직전 버전 검증에서도 같은 workbook을 다시 여는 구조를 줄였다.

적용 대상:

- 경영상태 저장
- 신용평가 저장

### 3. 신용평가 저장 후 업체명/지역 재조회 제거

기존에는 신용평가 저장 후 `companyName` 또는 `region`이 비어 있으면 백엔드가 다시 DB를 훑어서 메타데이터를 채웠다.

이 로직은 저장 응답 메타 채우기 용도의 안전장치였지만, 실제로는 `company_lookup` 비용이 다시 발생했다.

이번에 프론트에서 조회 시 이미 확보한 값을 저장 payload에 함께 실어 보내도록 바꿨다.

즉:

- 처음 사업자번호 조회에서 얻은 `companyName`
- 처음 사업자번호 조회에서 얻은 `region`

을 신용평가 저장 시 재사용한다.

이후 서버는 가능한 경우 재조회 없이 바로 저장/보관한다.

### 4. 프론트 저장 payload 보강

`ExcelWebEditPage.jsx`의 신용평가 저장 시점에 아래 값을 `data`에 함께 넣도록 수정했다.

- `companyName`
- `region`

이로 인해 백엔드의 fallback 재조회가 거의 타지 않게 됐다.

## 실제 로그 결과

### 변경 전

```text
[excel-edit:save] status=success fileType=신용평가 ... validate=1.29s credit_update=3.31s company_lookup=1.20s total=5.80s
```

### 중간 결과

```text
[excel-edit:save] status=success fileType=신용평가 ... validate=0.65s credit_update=3.31s company_lookup=0.00s total=3.96s
```

해석:

- `company_lookup` 재조회는 제거됨
- `validate`와 `company_lookup` 중복 오픈 비용은 크게 줄었음
- 남은 주된 비용은 여전히 `credit_update`

### 신용평가 세부 로그

전기/통신/소방 각각의 처리 시간도 확인했다.

예시:

```text
[excel-edit:credit] dbType=전기 stage=find outcome=updated elapsed=0.62s
[excel-edit:credit] dbType=전기 stage=save outcome=updated elapsed=0.58s
[excel-edit:credit] dbType=통신 stage=find outcome=updated elapsed=0.23s
[excel-edit:credit] dbType=통신 stage=save outcome=updated elapsed=0.21s
[excel-edit:credit] dbType=소방 stage=find outcome=updated elapsed=0.22s
[excel-edit:credit] dbType=소방 stage=save outcome=updated elapsed=0.22s
```

결론:

- 전기가 가장 무거운 것은 구조적으로 자연스럽다
- 통신/소방은 전기보다 가볍다
- 전체 병목은 DB를 실제로 반영하는 `credit_update` 자체다

## 최종 판단

이번 작업에서 안전하게 줄일 수 있는 비용은 대부분 줄였다.

특히 다음은 완료된 것으로 본다.

- 조회 시 중복 workbook 오픈 제거
- 저장 시 중복 workbook 오픈 제거
- 신용평가 저장 후 업체명/지역 재조회 제거

현재 남는 느림은 대부분 구조적인 작업량이다.

- 전기/통신/소방 3개 DB를 실제로 수정해야 함
- 전기 DB가 특히 큼

따라서 이 시점에서 더 공격적으로 건드리면 체감 개선보다 안정성 저하 가능성이 커진다.

## 다음 세션 인계 기준

더 이상 무리한 최적화는 하지 않는 것이 맞다.

다음 세션에서는 아래 기준으로 판단한다.

1. 기능 정확성이 먼저다.
2. 저장 완료 후 `company_lookup`은 0에 가깝게 유지되는지 본다.
3. `credit_update`는 구조상 일부 시간 소요를 허용한다.
4. 전기 DB 자체를 억지로 줄이기 위한 구조 변경은 보류한다.
